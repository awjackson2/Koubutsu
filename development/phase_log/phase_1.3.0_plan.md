# Phase 1.3.0 Plan — TestVideoSource and Shared Display Renderer

## Phase
- **Number:** 1.3.0
- **Name:** TestVideoSource + shared display renderer + synthetic test clip
- **Status:** Planned
- **Date drafted:** 2026-09-26

## Purpose
Milestone 2: play prerecorded Japanese video smoothly and in a loop, through the same display path live
capture will use, so everything downstream is exercised without hardware.

## Immediate Goal
1. `VideoFrame` — `CMSampleBuffer`/`CVPixelBuffer`-backed `TimedFrame` (no pixel copies).
2. `TestVideoSource: VideoSource` — `AVPlayer` + `AVPlayerItemVideoOutput`, pulled by a `CADisplayLink` on a dedicated thread, looping, host-time stamped, audio played by the player.
3. `SampleBufferRenderer` + `VideoDisplayView` — `AVSampleBufferDisplayLayer`, frames enqueued with display-immediately semantics.
4. `FramePipeline` — the single fan-out point from source to display (and, from 1.4.0/1.5.0, to OCR).
5. `AppModel` — `@MainActor @Observable` composition root: source selection, start/stop, lifecycle (scene phase), errors.
6. Synthetic clip `App/Resources/TestMedia/synthetic_ja_1080p60.mp4` + manifest (generated by `Tools/make_test_clip.py`), importing user footage via the Files importer into the app's Documents, and Finder file sharing.
7. `UVCVideoSource` placeholder conforming to `VideoSource` that fails with `.noDeviceAvailable` (implemented in Major 5).

## Confirmed Starting Point
- Core contracts from 1.2.0 (`VideoSource`, `FrameTiming`, `PipelineMetrics`, …). App shell from 1.1.0. Deployment target iPadOS 26.0.

## Scope For This Phase
### In
- Items above; minimal controls (source menu, import, play/stop) in `RootView`.
### Out
- Diagnostics panel (1.4.0), OCR (1.5.0), Metal rendering (only if measurements demand it).

## Recommended Implementation Direction
- Pixel format `420v` (bi-planar video range) with IOSurface backing — the format UVC capture devices commonly deliver, accepted by the display layer and Vision.
- Frames are wrapped in `CMSampleBuffer` with `DisplayImmediately` so the display layer shows them on arrival; no timebase, no added buffering — identical to how live capture frames will be shown.
- Looping via end-of-item notification + seek to zero (keeps one `AVPlayerItem` and its output).
- Frame `hostTime` = the host time the frame was pulled (the display-link target timestamp's host domain).
- Source lifecycle centralized in `AppModel`: background → stop, foreground → restart the selected source.

## Test Plan
- App tests (simulator, CI): bundled clip resolves; `TestVideoSource` starts, delivers ≥ 30 frames with strictly increasing sequence and host time, reports 1920x1080 and ~60 FPS format; stop halts delivery; missing file fails with `.mediaMissing`.
- Core tests unchanged and green.

## Key Decisions
- One display path for all sources (`AVSampleBufferDisplayLayer`), rather than `AVPlayerLayer` for test video.
- Display link on a dedicated thread (not main) so UI work cannot stall frame delivery.

## Expected Limitations At End Of Phase
- Display is not frame-paced against the panel's refresh beyond display-link cadence; measured in Major 4.
- No visual check other than CI tests; the user runs the simulator for visual confirmation.

Prerecorded video becomes a first-class `VideoSource` rendered through the same zero-copy sample-buffer path live capture will use.
